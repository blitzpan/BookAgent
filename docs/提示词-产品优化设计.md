## 硬性工作方式（务必遵守）
1. **先梳理，后设计**：分两个阶段执行，阶段一产出"现状事实"后必须停下来向用户汇报并等待确认，用户确认后才进入阶段二的方案设计。

3. **只读**：本次任务不得修改 `frontend/`、`backend/`、`reader/` 的任何源码，只能新增 `docs/` 下的文档。若发现 bug，写进文档的问题清单，不要顺手修。
4. **代码优先于文档**：当 `docs/`、`design/` 描述与代码实现不一致时，以代码为准，并在文档中显式标注「文档过时」的具体位置。
5. 探索阶段可用并行搜索/子代理加速，但所有引用必须回到真实文件核对后再写入文档。
6. **宁精勿多**：最终建议控制在 20 条以内。禁止输出"优化交互体验""提升系统性能""增强可扩展性"这类无法验收的抽象建议。

## 阶段二：优化设计（经我确认后执行）
基于阶段一事实，从**专业产品经理视角**提出优化方案。要求同时覆盖：
1. **页面布局与信息架构**：导航层级、页面分区、移动端适配、信息密度、主次任务是否清晰、长流程是否可中断/可恢复。
2. **交互与状态**：生成任务的长耗时反馈（进度/取消/重试/失败兜底）、空态与错误态文案、批量操作、二次确认、轻量化的即时快感（预览/流式结果）、无障碍与键盘操作。
3. **功能设计**：哪些"半成品"应该补完（尤其**热区能力 4** 的编辑端与落库是否有最低可行方案）、哪些缺失能力是用户真正的断点、哪些现有功能应当收敛或删除。
4. **前后端联动**：前端新交互需要哪些接口/字段变更；哪些前端痛点其实应下移到后端（如任务状态机、资产生命周期、幂等与重试、资源 CDN/缓存）；哪些后端设计制约了产品体验。
