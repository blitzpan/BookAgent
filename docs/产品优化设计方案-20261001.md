## 1. 摘要

**总目标**：让「从一句话故事到一本能在阅读器里点读的双语绘本」这条链路，从"能跑通"变成"敢托付"——不丢数据、不花冤枉钱、长任务可中断可恢复、热区能稳定做完并立刻验证。

**本期要解决的核心矛盾**：不是功能缺失（6 项核心能力均已落地，见 §E），而是**四类"已实现但形态不对"的债**——数据会被自己清掉、主流程有不可达分支、长任务不可控、热区的交付形态与阅读端消费方式不匹配。

**预期收益**（按可验证口径）

| 维度 | 现状 | 本期后 |
|---|---|---|
| 数据可靠性 | 后端每重启一次，`page_audio` 全表清空，配音进度归零 | 重启不丢；进度与磁盘文件一致 |
| 流程可达性 | 发布无完整性校验：缺图/缺文/缺音的书可以直接发布；反过来「生图部分失败」的书又永远发不了，且无补图兜底 | 发布前检查清单：图、文为硬门禁（缺则拒绝），配音与热区为软提示（⚠️ 但可发布，支持纯图文绘本）；始终失败的页可人工补图 |
| 钱 | 重启后重跑配音＝全书重新付费；点一次热区生成＝全书视觉模型重新付费 | 两处重复消耗消除；配音/重生成均有成本预告 |
| 热区 | 生成语义是"清空重跑"（与预期相反）；跨页改动静默丢失；无从知道哪些页还没热区 | 默认续跑；按页询问保存；覆盖率可见；编辑完一键跳转阅读端验证 |
| 阅读体验 | 图上热区是撑满页宽的文字块；图外文案不可点；双语模式吞英文 | 图外文案列表可点读（双语两行）；与图上热区双向联动；音频不叠加 |

**成本口径**：合计约 **16.4 人天**（P0 2.5 / P1 10.1 / P2 3.8）。**所有方案均不新增任何 AI 模型调用**，且其中 6 项直接减少现有调用量。

## 3. 核心矛盾提炼（5 条）

1. **一次重启就丢掉全部配音记录，并可能触发全书重新付费合成** —— `sqlite.ts:145-146` 每次启动重放 `schema.sql`，而 `schema.sql:131` 是 `DROP TABLE page_audio`；`audio_sets` 仍显示"已配音"但 `done` 归零，`audioExists` 判定失效。
2. **发布没有完整性闸门：该发的发不了，不该发的能发** —— ① 缺图/缺文本的书**可以直接发布**（`POST /:id/publish` 只校验状态、不校验资产完整性，`routes/runs.ts:119-138`），阅读端会看到空白页；② 反过来「生图部分失败」的书又永远发不了（`routes/runs.ts:126` 硬要求 `GEN_DONE`），续跑若始终失败则**无任何兜底**（无手动补图入口）；③ 状态机还留着 `生图部分失败 → 待审批发行` 这条与接口互相矛盾的边（`constants/status.ts:46-50`）。
3. **热区「生成」被实现成清空重跑，与「失败后继续」的预期相反** —— `routes/hotspots.ts:175` 默认 `regenerate: true` → `hotspotService.ts:263-268` 先 `DELETE ... WHERE source='ai'`，每次点击都是全书视觉模型重新计费。
4. **长耗时任务不可观测、不可中断、不可恢复** —— 5 处轮询各写各的（3s/2s/2s/2s/3s），补画阻塞 300s（`StoryDetail.tsx:429-440`），刷新后只有热区任务态能恢复（`:313-326`），后端全仓无 cancel。
5. **阅读端的消费形态与「点图发音」目标不匹配** —— 热区尺寸靠 label 文字撑开（`schema.sql:186-187` + `global.css:268`），双语模式下是大面积色块；图外文案列表已渲染但**不可点击**（`PageView.tsx:242-265`）；双语模式只出中文（`:248`）。

## 4. 优化方案详表（19 条）

> 分类：A 纯前端闭环 ／ B 前端为主需后端配合 ／ C 纯后端或架构优化
> 优先级：P0 止血（阻塞主流程）／ P1 体验短板 ／ P2 加分 ／ P3 暂缓
> 成本含自测，不含联调等待。

### P0 止血

#### S1 修复 `page_audio` 每次启动被清空
| 项 | 内容 |
|---|---|
| 分类 | **C** |
| 现状与证据 | `backend/src/db/sqlite.ts:145-146` 每次进程启动无条件 `db.exec(schema)`；`backend/src/db/schema.sql:130-131` 含 `DROP TABLE IF EXISTS page_audio;` → 每次重启清空全表。`audio_sets` 保留且 `status='completed'`（`:151`），磁盘 mp3 保留 → UI 显示"已配音 · 进度 0/N"自相矛盾，`ttsService` 的 `audioExists` 幂等判定失效 |
| 用户问题 | 单人创作者重启后端（日常操作）后，整本书的配音记录消失：详情页进度归零、试听列表变空；若此时点「继续生成」，**全书音频重新合成＝重复付费** |
| 解决方案 | ① 删除 `schema.sql:131` 的 DROP 行及其注释；② 旧库兼容沿用本文件既有手法——`PRAGMA table_info(page_audio)` 检测缺 `audio_set_id` 列才重建（参照 `sqlite.ts:164-169` 对 `page_hotspots` 旧列的处理）；③ 建议顺带把 `initDb` 改为"库文件不存在才建表，已存在则只跑 migra"（`sqlite.ts:138-146`），杜绝同类问题复发。<br>**接口/字段 diff**：无新增字段，无接口变更 |
| 优先级 | **P0**（影响面：全部有配音的书 × 发生频率：每次重启 ÷ 成本 0.5 人天） |
| 成本 | 0.5 人天；触及 2 个模块（`db/schema.sql`、`db/sqlite.ts`） |
| 验收标准 | ① 配音完成后重启后端 → `GET /api/stories/:id/audio-sets` 仍返回 `done === total`；② 重启后 `GET .../book-audio` 仍返回全部 `audioUrls`；③ 重启后点「继续生成」，`page_audio` 行数不增加（不重复合成） |
| 风险与回滚 | 历史库若存在无 `audio_set_id` 的旧 `page_audio`，需 migra 检测（已有同类代码可抄）；回滚＝恢复 DROP 行（不推荐）或删开发库重建。开关控制：无 |

#### S2 建立发布前的资产完整性闸门
| 项 | 内容 |
|---|---|
| 分类 | **B** |
| 现状与证据 | ① `backend/src/routes/runs.ts:119-138` 的 `publish` **只校验 `stories.status`**（`:126` 要求 `GEN_DONE`），**完全不校验资产完整性**——缺图、缺文本、没配音的书都能直接发布；② 反过来「生图部分失败」的书又发不了（同一行 `:126`），而续跑若始终失败则无兜底（已核实续跑链路本身是自洽的：`generationService.ts:709` `skipExisting:true` 只补失败页，补齐后 `:763` 判 `completed` → `GEN_DONE`，因此可自愈）；③ `backend/src/constants/status.ts:46-50` 留着 `生图部分失败 → 待审批发行` 这条与接口矛盾的边；④ 前端 `StoryDetail.tsx:524` 只按状态渲染按钮，无任何"还差什么"的提示 |
| 用户问题 | 按正确流程（写故事 → 生图 → 配音 → 配热区 → 人工核对 → 审批发布），发布是最后一道人工闸门。现在的闸门是坏的：**缺口的东西能发出去**（阅读端出现空页/无声），**而部分失败的书又卡死**（不知道缺哪页、补不了、发不出）。人工既不能确认"齐了没"，也没有补齐手段 |
